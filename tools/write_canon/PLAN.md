# WRITE-CANON-1 plan

Authorized by the owner on #1169, comment 7080958038 (`amaybaum`, 2026-11-22T14:59:31Z), as
research and implementation only. Goal link: housekeeping. The tool does not replace the existing
comment helpers, which remain the validated path.

## Scope

One standard-library Python tool, `write_canon.py`, with an offline test suite, under
`tools/write_canon/` only. No file of the A1 retirement ledger is touched; AGENTS.md, `papers/`,
`book/` and `.github/` are unchanged.

- **check** writes nothing to GitHub. It validates a source body and, optionally, a stored body
  against it.
- **post** writes one Issue comment through
  `gh api -X POST repos/amaybaum/incompleteness/issues/<n>/comments -F body=@<file>`, and nothing
  else. It is never run by the tests.

## Design

1. **Normalization.** With `F = _Generated by [Claude Code](https://claude.ai/code)_`, `core(s)`
   strips trailing newlines and then removes one trailing `"---\n" + F` together with the newlines
   before it, only when it follows a blank line or is the whole body (so `"x---\n" + F` and the
   setext form `"Title\n---\n" + F` keep every byte); `N(s) = core(s) + "\n\n\n---\n" + F`. N is
   the identity on every byte of `core(s)`, which is a prefix of `s`, and `N(N(s)) = N(s)`. CR,
   NUL, every other control character except `\n` and `\t`, and every non-ASCII whitespace
   character are rejected, as is invalid UTF-8.
2. **Classification, never rewriting.** A small, conservative scanner over `core(s)` recognizes
   code spans (equal-length backtick runs), fenced code blocks, bold, flat and nested `-` lists,
   tables, bare URLs and inline links. The allow-list is exactly what the real path has tested:
   bold paragraphs, flat and nested bullet lists, tables, code spans, a bare full-SHA blob link,
   inline links to Issue, pull request and comment pages, and the literal `[text](` + code span +
   `)` form of the #1548 receipt. Anything else, or anything the scanner is unsure of, is
   UNSUPPORTED and fails: headings, raw HTML, entities, escapes, images, reference links, block
   quotes, setext underlines, thematic breaks, ordered lists, indented code, emphasis other than
   bold, strikethrough, mentions, emoji shortcodes, trailing whitespace, invisible format
   characters, and recognized but untested constructs such as fenced blocks. The footer's `---`
   is allowed only as part of the footer.
3. **Three checks, reported separately:** (a) source integrity (hashes, forbidden characters,
   and, for a stored body, byte identity with `N(source)`); (b) link validity; (c) the construct
   inventory. A byte match is not reported as establishing (b) or (c).
4. **Links.** A full blob URL outside code is checked against its own repository: for
   `amaybaum/incompleteness`, locally with `git` in a sanitized environment (commit object, path
   is a blob, commit reachable from a `refs/remotes/origin/*` ref); for any other repository it is
   UNVERIFIED and fails unless `check --online` is given, which makes one read-only
   `gh api repos/<o>/<r>/contents/<path>?ref=<sha>` GET. Post mode accepts only locally verified
   links. A shortened or ellipsis blob
   URL is allowed only inside a code span; a blob URL as an inline-link destination is rejected
   (the observed corruption). Nothing is expanded or replaced.
5. **Post.** Fixed endpoint template; the Issue number is a positive integer and must not be a
   pull request (read-only GET first). Refuses on a halt or pending marker, on a held lock, and on
   any check failure. State files (lock, halt, pending, submitted copy) live in a fixed per-user
   directory with no path argument; symlinks are refused for the source, the state files and the
   receipt (`O_NOFOLLOW`, `lstat`). The validated bytes are copied into the state directory and
   that copy is what `gh` reads. A pending marker is created (`O_CREAT|O_EXCL`) before the write
   and removed only after verification succeeds; a leftover one counts as a halt. After the
   write the comment is fetched by id and compared byte for byte, its blob links re-checked, and
   `created_at == updated_at` checked. Any mismatch, missing or non-JSON response, ambiguous
   result or error after submission writes the halt file atomically and exits nonzero, with no
   retry. The receipt is written atomically and states that detection happens after the write
   and is not prevention. `gh` is reached through an injectable runner, so tests make no network
   calls.

## Tests (`python3 -I -m unittest discover -s tools/write_canon`)

- every fixture: the blob-link round trip and the #1548 receipt (Unicode ellipsis in a code span,
  preserved as exact UTF-8), both real, and a synthetic submitted and stored pair reproducing the
  #1169 backtick-wrap corruption;
- idempotence of N on every fixture and on repeated, missing, one-blank-line, rule-only,
  footer-without-rule, footer-plus-text and double footers; trailing newlines; byte identity
  outside the footer;
- CR, NUL and control characters;
- nested and multi-backtick code spans, unequal runs, backticks in link text, code spans across
  lines, escaped backticks, entities;
- full, shortened, foreign-repository and nonexistent blob links;
- corruption mutants the verifier must catch: backtick-wrapped link, appended footer, CR
  insertion, trailing whitespace, dropped bytes;
- malformed Markdown (unbalanced backticks, stray pipes), lists in tables and tables in lists,
  and every unsupported construct failing closed;
- post-mode stubs: matching store, modified store, missing response, network error after
  submit, non-JSON, existing halt file, leftover pending marker, held lock, symlinked source and
  receipt, pull-request number, and no retry in any failure;
- the post command cannot target anything but an Issue's comments.

## Acceptance criteria (owner comment 7080958038)

- All non-footer bytes are unchanged.
- Normalization is idempotent.
- Unsupported constructs fail closed.
- The known corruption patterns are detected.
- Post-write verification cannot silently accept a modified body.
- The tool does not broaden existing write permissions.

Additional requirements from the same comment: formatting preservation is kept separate from
semantic validity, with separate checks for source integrity, link validity and rendering-related
classification; link validation is repository-aware; failure handling is conservative (an
unexpected stored-body difference, a missing verification response or an ambiguous result halts;
a network failure after submission never retries; the halt file is created atomically).
