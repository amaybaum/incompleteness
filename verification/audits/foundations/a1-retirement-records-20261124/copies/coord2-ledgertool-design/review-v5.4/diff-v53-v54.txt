> **Configuration admission and the root of trust (O5, B3, V2; owner decisions D1-D5 of
> 2026-11-23, called A-D1 to A-D5 here).** Neither the caller nor `F` can establish who designated
> `F`, in which repository, or by which workflow. These authority values come from one reviewed
> record, the **tool authority record** `A`, which the caller cannot override and a frozen plan can
> never redefine.
> 
> **The authority record `A`** (schema `oi-tool-authority/1`). `A` lives at the fixed path
> `tools/ledger_coverage/authority.json`, a generic location of the tool's own data, not a
> retirement record, and outside the engine's purity scope. It lands on `main` through its own
> independently reviewed and owner-authorized landing, before any freeze (sec. 6.3 chain). For A1 it
> pins:
> 
> - `owner`: the numeric user id 7273571 (login `amaybaum`, recorded for readers) (A-D1);
> - `repository`: the numeric repository id 1156244443 (full name `amaybaum/incompleteness`), which
>   must not be a fork (A-D4);
> - `workflow`: the exact path and the sha256 of the content of the one workflow whose runs may
>   produce an acceptable result (A-D4);
> - `plans`: for each plan, its `plan_id` and the authorized thread (repository id and issue number),
>   and the allowed `round` ids (A-D3);
> - `forms`: the exact designation, withdrawal and supersession forms (A-D3), below.
> 
> The owner identity is never derived from the repository owner, the caller, the environment or the
> frozen plan (A-D1).
> 
> **The trust root, without circularity (addendum of 2026-11-23).** `A` is data. It cannot
> authenticate itself, and the owner id inside it cannot be what authenticates it. Its authority rests
> on three things outside `A`, the caller and `F`:
> 
> 1. **The host's attestation of the run's repository.** In a host CI run, the tool and the consumer
>    each read the run record from the host API, by the run id the host assigns. That record states
>    the numeric id of the repository the run executes in. This is the host's attestation; nothing in
>    the run's own output, the caller's arguments or the environment is read for it.
> 2. **That repository's `main`, read through the host API.** The tool reads `A` only from the
>    default branch `main` of the attested repository, by the host's API, at the commit the host
>    reports as `main`'s head. It never reads `A` from the caller's checkout, from another ref, from
>    another repository, from a file the caller supplies, or from `F`'s tree. `A.repository` must
>    equal the attested repository id, and the host must report that repository as not a fork; this
>    is a consistency check of `A` against the attestation, not a source of trust.
> 3. **Acceptance happens in the canonical repository.** A result is accepted only by its landing on
>    `main` of the repository in which the owner lands it (A-D5). The consumer, the landing check run
>    in that repository, reads `A` from that repository's `main` itself (point 2) and requires the
>    producing run's attested repository id (point 1) to equal it. So a run in a fork or another
>    repository, even with a self-consistent `A` of its own, can never be accepted.
> 
> **Bootstrap order.**
> 
> - `A` lands on `main` of the canonical repository through its own pull request, independently
>   reviewed, authorized by the owner and merged, before any freeze. The tool records the merge
>   commit and the host's merged-by numeric id, and requires that id to equal `A.owner`. This is a
>   consistency check: the first version of `A` cannot be authenticated from its own content.
> - Every later change to `A`'s path on `main`'s first-parent chain must be such a merge, with its own
>   review record and owner authorization (sec. 6.3), merged by the numeric id that the previous `A`
>   pins. A change that is not refuses admission until it is reviewed and authorized.
> - The tool does not accept any other way of establishing `A`.
> 
> **Changes between `F` and execution.**
> 
> - `F` must descend from a `main` commit that already contains `A`, so `F`'s tree holds a copy of
>   `A`. If `F`'s tree has no `A`, the run is refused.
> - If `main`'s current `A` equals `F`'s copy, that `A` governs.
> - If they differ, the run is refused, unless every change to `A` on `main` after the commit `F`
>   descends from is a reviewed, owner-authorized merge as above. In that case the current `main` `A`
>   governs, and `result.json` records both blobs and the merges between them.
> - A change that is not reviewed and authorized fails closed (control TR26). A frozen plan can
>   therefore never redefine the authority rules: `F`'s copy of `A` never governs on its own, and it
>   is never read in place of `main`'s.
> 
> **The caller cannot override.** No command-line option, environment value, configuration field or
> record in `F` can set or override `owner`, `repository`, `workflow`, `plans` or `forms`. The
> retirement configuration (sec. 16.2) cannot contain these fields; an unknown field there is ERROR
> `CONFIG_INVALID`. A configuration the caller supplies as a file or path is never read as `A`
> (control TR24).
> 
> **Residual trust assumptions, stated.** The tool and the consumer trust:
> 
> - the host's API and its attestations: the run's repository id, the repository's fork status, the
>   head of `main` and the content of its files, a pull request's merged-by id, a comment's
>   immutable id, numeric author id, creation time, edit history and hidden state, and the complete
>   listing of a thread;
> - the host's access control on the canonical repository's `main`: only merges that the repository's
>   rules admit change it;
> - the integrity of the first, reviewed and owner-merged landing of `A`, which nothing in the tool
>   can verify from `A`'s content;
> - the owner's own account.
> 
> If any of these fails, the tool's checks can be deceived. None of them is a value the caller can
> choose.
> 
> **The forms (A-D3).** A designation, withdrawal or supersession is a host comment whose first line
> is exactly one of the following, where `<F>` and `<F2>` are full 40-hex commit ids:
> 
> - `Designate freeze <F> for plan <plan_id> round <round_id>`
> - `Withdraw freeze <F> for plan <plan_id> round <round_id>`
> - `Supersede freeze <F> with <F2> for plan <plan_id> round <round_id>`
> 
> `<plan_id>` and `<round_id>` must be ones `A` lists. The forms themselves are fixed by `A`, and the
> exact strings above are the A1 values `A` carries. A *plan id* names one retirement plan, together
> with its authorized thread. A *round* names one freeze cycle of that plan; at most one `F` is valid
> per plan and round. Both are defined in `A`, never in `F`. A comment written for another purpose
> cannot match these first lines.
> 
> **Admission.** The tool performs the following inside a host CI job; any step that fails or cannot
> be completed refuses admission with ERROR `CONFIG_UNREVIEWED`:
> 
> 1. **Repository and run.** The tool reads its own run record from the host API, and `A` as the trust
>    root above prescribes. The run's attested repository id must equal `A.repository`, and that
>    repository must not be a fork. The workflow
>    path must equal `A.workflow.path`, and the sha256 of that file's content at the run's `head_sha`
>    must equal `A.workflow.sha256`. The name of a workflow or job never counts.
> 2. **The thread, read completely.** The tool reads every comment of the authorized thread of the
>    plan named by the run (`--plan <plan_id>`, which only selects among `A`'s plans), page by page
>    until the host reports no further page. The number read must equal the thread's comment count
>    as the host reports it; a mismatch, a page error or an unavailable API refuses.
> 3. **Relevant comments.** A comment is relevant if its author's numeric id equals `A.owner` and its
>    first line starts with `Designate freeze`, `Withdraw freeze` or `Supersede freeze`. A relevant
>    comment whose first line is not exactly a valid form for this plan refuses: it is ambiguous. A
>    comment whose author has the owner's login but another id is not the owner's, and is reported.
> 4. **Edit status (A-D2).** For every relevant comment, the tool records its immutable comment id,
>    author numeric id, creation time and edit status. The edit status is the REST `updated_at` and
>    the GraphQL `lastEditedAt` and `userContentEdits` count. A designation comment with any edit
>    ever recorded is permanently invalid, even if its original text was restored. A replacement
>    needs a new comment. A relevant comment of any kind that is hidden or minimized, or whose edit
>    status cannot be read, makes the round's state unverifiable, and admission is refused.
> 5. **Deterministic state.** The relevant comments for this plan and round are processed in order
>    of creation time, then comment id:
>    - a designation of `F` makes `F` designated, unless it is invalid under point 4;
>    - a withdrawal of `F` makes it withdrawn;
>    - a supersession of `F` by `F2` withdraws `F` and designates `F2`.
> 
>    The run's `F` is admitted only if, at the end, it is the one designated commit of the round.
>    Refusal is fail-closed. Any of the following refuses: two live designations; a withdrawal or
>    supersession naming a commit that was never designated; a designation of a commit already
>    withdrawn; any other conflict.
> 6. **The pin table.** The tool reads `F`'s PREREG pin table from `F`'s tree, at the path `A` names
>    for the plan. Its content is authenticated by the owner's designation of exactly `F`. The
>    retirement configuration, its review record and its owner authorization are admitted only if
>    listed there with their sha256. Files beside the configuration are never admitted.
> 7. **The owner field.** `retirement.owner` must equal `A.owner`, and the owner of the configuration's
>    authorization record must equal it as well.
> 8. **Optional equality.** `--config-sha256`, if given, must equal the admitted configuration's
>    sha256. It is an extra check and never a substitute.
> 9. **Local runs.** A run outside a host CI job, or one that cannot reach the host API, cannot reach
>    `"chain"`. The host being unavailable is a refusal, never a fallback.
> 
> `result.json` records `config.admission`. The value `"chain"` is written only when points 1-7 held,
> with:
> 
> - `A`'s blob sha256 and the merge commit that last changed it;
> - the run's repository id, workflow path and workflow content sha256;
> - `F`, and every relevant comment, each with its id, author id, creation time, edit status and
>   first-line sha256;
> - the pin table's `{path, blob_sha256}`.
> 
> Only `"chain"` is acceptable (sec. 5). The control harness (sec. 10.4) may admit a draft
> configuration without its chain. Its results carry `"admission": "control-harness"` and are never
> written as an acceptable result.
