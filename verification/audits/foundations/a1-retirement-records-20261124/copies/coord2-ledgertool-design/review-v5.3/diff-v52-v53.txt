< **Semantics of `register` and `infinity` (D6).** These two profiles reproduce items 5 and 6 of P's
< plan, which compare a replacement with the text it replaces (P's `edits_check.py`, `static_new`,
< lines 351-380). Matching the image alone would flag wording that was already present in the

< - **`register`** (REG): a FAIL for each lowercased REG token that occurs in the image and does not
<   occur in the replaced text (set difference).
< - **`register-caps`** (CAPS less CAPS_OK): as `register`, for capital tokens, and only for splices
<   whose edit kind is one of the kinds named in the rule file (A1: `ptr`, `consistency`, `handoff`).

> **Semantics of `register` and `infinity` (D6, V1).** These profiles implement items 5 and 6 of P's
> plan exactly as P's frozen checker defines them: per edit and per step of the edit list, not per
> splice. The reference is P's `edits_check.py` (blob sha256 2856e58c...d98c), function `static_new`
> (lines 351-380), with `inf_key` (lines 345-349) and `sentences` (lines 227-228). No approximation is
> admitted.
> 
> - **Unit.** For every entry `e` of the edit list frozen at `F` (`edits.json`, read through the
>   ledger adapter's companion and bound by `edits_sha256`), the pairs evaluated are `(e.old, e.new)`
>   and, if `e` has a second step, `(e.old_step2, e.new_step2)`. Each pair is evaluated separately.
>   Edits that the ledger lists as retained (A1: D032, D039) have no image and are evaluated as P does
>   (`old` against `new`).
> - **`register`** (REG): a FAIL for each lowercased REG token in `new` that is not among the
>   lowercased REG tokens of `old` (set difference per pair).
> - **`register-caps`** (CAPS less CAPS_OK): a FAIL for each CAPS token in `new` that is not in `old`
>   and not in CAPS_OK, only when the edit's own `kind` is one of the kinds named in the rule file
>   (A1: `ptr`, `consistency`, `handoff`).
> - **`infinity`** (INF less NEUTRAL): each of `new` and `old` is split by **P's splitter**,
>   `re.split(r'(?<=[.;:?])\s+', text)`: a sentence ends after `.`, `;`, `:` or `?` followed by
>   whitespace. This is not splitter version 2 of sec. 6.1, which does not split at `;` or `:` and so
>   would change which NEUTRAL spans exempt a match. In each sentence, every INF match not contained
>   in a NEUTRAL span is an assertion. `old` is first rewritten as P rewrites it (A1:
>   `\bA1\b(?: \(finiteness\))?` becomes "finiteness"). Each assertion is normalized to a key as P's
>   `inf_key` does (lowercase; runs of whitespace, `*` and `_` collapsed to one space; a key matching
>   `finiteness\b.*\bfails` becomes "finiteness fails"). A FAIL is emitted for each assertion of `new`
>   whose key count in `new` exceeds its count in the rewritten `old` (multiset difference, in P's
>   order).

>   `H` bytes it replaces, same rules) also runs, and a FAIL from either unit is a FAIL. In addition,
>   the integrity stage checks the correspondence of edits and splices: every splice names exactly one
>   edit of the same file; every edit is either a splice's edit or listed as retained; for an edit
>   without a second step, the splice's replaced bytes equal `e.old` and its image equals `e.new`; for
>   an edit with a second step, the splice's replaced bytes equal `e.old` and its image equals the
>   result of both steps. Any other relation (a splice covering two edits, an edit split over two
>   splices, an unlisted edit) is ERROR `SOURCE_CHANGED` with the edit and splice ids, so neither unit
>   can silently differ from the other.

> **The fingerprint's context and location (V5).** The sentence list of a file is every sentence of
> every paragraph, in file order, under splitter version 2 (sec. 6.1); neighbours may lie in adjacent
> paragraphs. For the sentence at index `k`, `prev` is the sentence at `k-1`, or the four bytes `BOF`
> if `k` is the first; `next` is the sentence at `k+1`, or `EOF` if `k` is the last. Each sentence is
> taken as the splitter yields it (lines stripped and joined with one space) and encoded as UTF-8.
> `context_sha256 = sha256(prev || 0x00 || next)`. "Location" in step 3 means exactly this pair of
> neighbours in the named file. It is not a line number or byte offset: a shift of the whole region
> (control WB8) keeps the allowance, and so does a move of the sentence together with both of its
> neighbours to another part of the same file, since the approved text and its approved neighbours
> travel together (control WB13, expected PASS). A move of the sentence without both neighbours
> changes the context and loses the allowance (WB5).
> 
> **One grant, deterministically (V5).** When several sentences in one file satisfy the conditions of
> step 3 for the same fingerprint (identical text with identical neighbours), the grant goes to the
> one with the smallest byte offset in the file; every later one gets no allowance (control WB14).
> 
> **Case (O1).** Literal entries of an allow rule's negative matcher are matched case-insensitively,
> for W1, W2 and every other allow rule; a regex entry keeps its own flags. Allowances count
> case-insensitive matches. Measured at T1': no W1 or W2 sentence gains a match (W1-c keeps exactly
> one `finit` match), so no outcome on the real tree changes, while a capitalized edit such as an
> added "Finiteness" becomes FAIL `rule-negative-match` (control WB15).

> **Configuration admission and the root of trust (O5, B3, V2).** Neither the caller nor `F` itself can
> establish who designated `F`. A commit cannot contain its own designation, because its id is unknown
> when it is written, and any record inside `F`'s tree was written by whoever made `F`. The authority
> is therefore read from outside both:
> 
> 1. **The designation is a host comment by the owner.** `F` is designated only by a comment of the
>    owner on the host, in the thread the plan amendment names (sec. A.39 item 1), whose body contains
>    `F`'s full 40-hex id in the designation form the plan amendment fixes. The tool reads it itself
>    from the host API, inside the CI job (sec. A.44), over the host's own endpoint, and records the
>    comment id, author login, creation time and body sha256.
> 2. **The owner's identity comes from the host, not from the caller.** The owner login is the owner
>    of the repository in which the CI job runs, as the host's API reports it for the repository the
>    job's own run record names. It is never taken from a command-line argument, an environment value
>    the caller sets, the configuration, or `F`'s tree. The comment must be authored by that login
>    and carry the host's owner association.
> 3. **The comment checks.** All must hold, or admission is refused with ERROR `CONFIG_UNREVIEWED`:
>    - the comment exists at the stated id in the named thread;
>    - its author is the owner of point 2;
>    - its body quotes exactly one full commit id, and it equals `F`;
>    - it has not been edited after creation (`updated_at` equals `created_at`);
>    - no later comment of the owner in the same thread designates another commit for the same round
>      or withdraws this designation (the tool reads the whole thread, so the caller cannot pick an old
>      comment).
> 4. **The pin table.** The tool reads `F`'s PREREG pin table from `F`'s tree at the path the plan
>    amendment fixes. Its content is authenticated by the owner's designation of exactly `F` (point
>    3), not by any record inside it. The configuration is admitted only if its path and sha256 are
>    listed there, and its own review record and owner authorization only if they are listed there
>    too. Files beside the configuration are never admitted.
> 5. **The owner field.** `retirement.owner` must equal the owner of point 2, and the owner of the
>    configuration's authorization record must equal it too.
> 6. **Optional equality.** `--config-sha256`, if given, must equal the admitted configuration's
>    sha256. It is an extra check, never a substitute.
> 7. **Local runs.** A run that cannot read the host API from inside a host CI job (any local run)
>    cannot reach `"chain"` admission. It is ERROR `CONFIG_UNREVIEWED`, or, through the control
>    harness, a control result that is never acceptable.
