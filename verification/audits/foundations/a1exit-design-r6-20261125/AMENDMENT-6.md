## 1. A review-record finding (R6.RECON.26, second kind)

Options:

- (a) The verdict entry on `<path>:scientific_effect` counts as a finding whenever it carries a non-empty `invalidated`, whatever its verdict value. Safe against loss, but it makes an `accept` that also lists `invalidated` ambiguous.
- (b) A dedicated verdict value, `invalidates`, plus `invalidated`. Unambiguous. Using `reject` instead would overload a value that also means "wrong for other reasons", so a plain rejection could not be told from a finding.

Proposal: (b) with the value `invalidates`, permitted on `scientific_effect` items only. Review-record lint (the review as a record) is separate from the reviewed record's chain lint: the finding makes the reviewed record not apply, while the review stays valid. Any `invalidated` with another value, or `invalidates` with an empty or malformed list, is a form failure that still blocks (over the edits the entry's conclusions name, or every edit of the path), so no form error can lose a finding. Reasoning: R6.RECON.26 already says the review "finds that the change invalidates", and R6.REC.6 makes every non-`accept` verdict a failure of the reviewed record, so a separate value fits both without changing R6.REC.6.

Controls: FINDING-FORM.

## 2. Lineage scope

Options:

- (a) Bind every configuration whose ledger carries the edit. Never loses a block, but over-blocks another retirement that reuses the edit id.
- (b) The finding names the configuration it was made under, `{path, blob_sha256}`; the lineage of amendment 4 is computed from it.

Proposal: (b), with (a) as the fail-closed fallback: a finding without a readable `configuration` is a form failure and binds every configuration carrying its edits. Reasoning: amendment 4 defines the lineage from "the configuration the finding was made under", which only (b) makes readable from git objects; the fallback keeps the owner's rule that a finding cannot be lost.

Controls: FINDING-LINEAGE.

## 3. Where a recorded migration lives

Options:

- (a) No location: only the path-and-old-bytes match is implementable. The owner's row "Block follows the recorded migration" would then rest on the mechanical match alone, and a rename that also rewrites the old bytes would escape it.
- (b) A reviewed record `oi-edit-id-migration/1`, referenced by the configuration with kind `edit-id-migration`, followed through the `supersedes` chain.

Proposal: (b), with the mechanical match kept in addition, so a missing or invalid migration record can never lift a block; a mapping only adds edits. Reasoning: AGENTS.md sec. A.48 item 3 requires the migration to be recorded and approved; reading it from the configuration's references keeps it pinned at the freeze.

Controls: MIGRATION-RECORD.

## 4. Key names inside `invalidated`

Options:

- (a) `{id, sha256}` as the amendment-3 code reads: loses the target that amendment 4 requires for the path-and-old-bytes match.
- (b) The writer's proposal `{id, sha256, target: {path, start_H, old_sha256}}`, the target copied from the ledger splice of the same id at `H`.

Proposal: (b). Each splice id of the retirement ledger is unique (399 splices, no repeated id), so one target per id suffices. A mismatch or a missing key is a form failure that still blocks the id.

Controls: FINDING-KEYS.
