## 1. The tool writer's points 1 to 5

### 1. A review-record finding (R6.RECON.26, second kind)

Options:

- (a) The verdict entry on `<path>:scientific_effect` counts as a finding whenever it carries a non-empty `invalidated`, whatever its verdict value. Safe against loss, but it makes an `accept` that also lists `invalidated` ambiguous.
- (b) A dedicated verdict value, `invalidates`, plus `invalidated`. Unambiguous. Using `reject` instead would overload a value that also means "wrong for other reasons", so a plain rejection could not be told from a finding.

Proposal: (b) with the value `invalidates`, permitted on `scientific_effect` items only, and detection before lint (r2, review finding 3): any non-author review carrying `invalidates` or `invalidated` on any item counts; every lint failure other than an independence failure is a form failure that still blocks. Reasoning: R6.RECON.26 already says the review "finds that the change invalidates", and R6.REC.6 makes every non-`accept` verdict a failure of the reviewed record, so a separate value fits both without changing R6.REC.6.

Controls: FINDING-FORM.

### 2. Lineage scope

Options:

- (a) Bind every configuration whose ledger carries the edit. Never loses a block, but over-blocks another retirement that reuses the edit id.
- (b) The finding names the configuration it was made under, `{path, blob_sha256}`; the lineage of amendment 4 is computed from it.

Proposal: (b) for the id and migration matches, with the path-and-old-bytes match applied to every configuration whatever its lineage (r2, review finding 1), and (a) by id, migrated id or target as the fail-closed fallback (review finding 2). Reasoning: amendment 4 defines the lineage from "the configuration the finding was made under", which only (b) makes readable from git objects; the global target match closes the fork escape; the fallback keeps the owner's rule that a finding cannot be lost.

Controls: FINDING-LINEAGE.

### 3. Where a recorded migration lives

Options:

- (a) No location: only the path-and-old-bytes match is implementable. The owner's row "Block follows the recorded migration" would then rest on the mechanical match alone, and a rename that also rewrites the old bytes would escape it.
- (b) A reviewed record `oi-edit-id-migration/1`, referenced by the configuration with kind `edit-id-migration`, followed through the `supersedes` chain.

Proposal: (b), with the mechanical match kept in addition, so a missing or invalid migration record can never lift a block; a mapping only adds edits. Under (b) a rename that also rewrites the old bytes is caught only when its migration is recorded and referenced; otherwise the residual of R6.RECON.26 remains (it rests on the review of the new freeze). Reasoning: AGENTS.md sec. A.48 item 3 requires the migration to be recorded and approved; reading it from the configuration's references keeps it pinned at the freeze.

Controls: MIGRATION-RECORD.

### 4. Key names inside `invalidated`

Options:

- (a) `{id, sha256}` as the amendment-3 code reads: loses the target that amendment 4 requires for the path-and-old-bytes match.
- (b) The writer's proposal `{id, sha256, target: {path, start_H, old_sha256}}`, the target copied from the ledger edit of the same id at the named configuration's `H`.

Proposal: (b), with `id` an edit id of the edit list (a retained edit included, its target the occurrence of its text at `H`; audit ranked item 2). A mismatch or a missing key is a form failure that blocks through the fallback.

Controls: FINDING-KEYS.

### 5. RECON-BLOCK versus amendment 4

Options:

- The RECON-BLOCK countercase expected no block for a revised plan that only changes the edit's entry; amendment 4 keeps the block for a wording change unless the freeze cites an applying reassessment.

Correction: the RECON-BLOCK countercase now requires the cited reassessment naming the finding, and a case is added in which a wording change without a reassessment stays blocked. This follows R6.RECON.26 as amended by amendment 4, which governs over Table 17.1.

Controls: RECON-BLOCK.

Options:
