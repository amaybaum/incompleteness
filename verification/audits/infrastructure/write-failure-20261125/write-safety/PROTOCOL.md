# Automated GitHub writes: investigation of the 2026-11-25 failure, and a correction and validation protocol

Local, paper-only work under the owner decision of 2026-11-25 (amaybaum, coordinating session):
"I authorize the four actions as listed." The action covered here is to investigate both defects
and prepare the correction and validation protocol, keeping the automated text-write halt and
leaving AGENTS.md §A.49 and the affected Issue bodies unchanged.

No GitHub write, push or commit was made in this work. Every GitHub access was a read-only REST
GET. Files named below are in the same directory as this document.

Evidence read: branch `evidence/write-failure-20261125` at
`44b8df0c88b6a2d43e62be64d53cdbdfcf227861`, directory
`verification/audits/infrastructure/write-failure-20261125/`. Its `SHA256SUMS` verifies for all
18 files; a local copy is in `ev/`.

## 1. Findings

### D1. Text changed before storage

**What the evidence shows (re-verified byte for byte).** For #1558, #1062, #1245 and #1556 the
stored body equals the sent body followed by exactly
`"\n\n---\n_Generated by [Claude Code](https://claude.ai/code)_"` (58 bytes), and differs in no
other byte. None of the four sent bodies ended with that footer, and none had a trailing newline.
#1565, whose sent body already ended with the footer, was stored unchanged. The rule consistent
with all five is "append the footer if the body does not already end with it".

**Where the request was built.** `edit.py` built the JSON body in Python and passed it to
`gh api -X PATCH ... --input -` on standard input. No shell command string carried the text. So a
change at the level of a Claude Code tool call (a hook rewriting the Bash command) cannot have
altered it; the change happened in `gh`, or in the HTTP path after `gh`, or at GitHub.

**Read-only facts about each locus.**

| Locus | Facts found | Assessment |
|---|---|---|
| `gh` | `/usr/local/bin/gh` is gh 2.89.0, a static binary, first on `PATH` after an `rm`-only guard directory. No `gh` config, aliases or extensions exist. The binary contains no `Generated by` string. | Ruled out for practical purposes. |
| Claude Code (settings, hooks, local proxy) | Repository settings set `attribution.commit` and `attribution.pr` to `""` and `sessionUrl` to false. No user or local settings file exists; the launcher settings define only a SessionStart and a Stop hook, and neither script contains the footer. The local proxy listening on the `HTTPS_PROXY` port is part of the Claude Code process. The Claude Code binary contains no copy of the footer text, `_Generated by`, `Generated by [` or `claude.ai/code)_`, in UTF-8 or UTF-16. Its only attribution generator produces a different text (`Generated with [Claude Code](...)`, with an emoji prefix) and a session link. The proxy documentation says TLS is re-terminated at the egress proxy, not locally. | Unlikely. Runtime-built strings cannot be excluded by a string scan, but nothing local produces this text. |
| Egress proxy (outside the container) | The certificate presented for `api.github.com` is issued by `CCR agent-proxy interception CA (production) 2026-08`, so the egress layer sees request bodies in plaintext. `GH_TOKEN` and `GITHUB_TOKEN` in the container are 14-character placeholders, and requests reach GitHub authenticated as the owner through the `claude` GitHub App. The proxy therefore already rewrites every request by injecting the credential. The agent-proxy software supports request hooks (the Claude Code binary carries setup text for a self-hosted agent proxy with "hooks"). | **Most likely locus.** |
| GitHub | GitHub stores Issue and comment bodies as sent; it has no feature that appends text for an App. Writes by the other App on this repository carry no footer. | Unlikely. |

**Corpus survey (read-only GETs; `comments-survey.tsv`, `issues-survey.tsv`).**

- Issue comments since 2026-10-15 made through the `claude` App: 3,214. Every one ends exactly
  with the footer. Comments through `chatgpt-codex-connector`: 1,283, none ending with it.
  Agents are unlikely to have added an identical footer by hand to every comment for six weeks,
  so the footer is probably supplied on the comment path as well. Sent texts that included it
  were stored unchanged, which is consistent with append-if-absent.
- Issues and pull requests created through the `claude` App: of those created before
  2026-11-19, 22 of 367 current bodies end with the footer; of those created from 2026-11-21,
  88 of 91 do. The change took place with no change in the container. That fits a server-side
  change of rule in the path, starting about 2026-11-19 to 2026-11-21, for bodies of Issues and
  pull requests. It is not proof: current bodies may have been edited since they were created,
  and agents may have added the footer themselves.
- Earlier observation (AGENTS.md §A.49 rule 2): a pull-request description edited through the
  GitHub connector had a footer removed. Connector traffic reaches GitHub through a different
  route; the local agent proxy does not carry it, because the connector host is in `NO_PROXY`. So
  at least two paths handle this footer, by different rules: append on the REST path and removal
  on a connector edit.

**What each hypothesis predicts.**

- *Egress proxy:* append-if-absent on body fields of REST writes sent with the injected
  credential, whatever client sends them. No change to text that already ends with the footer.
  No effect on the connector route, which has its own handling. Rule changes happen without any
  change in the container.
- *GitHub:* the same footer would appear on writes made with the `claude` App credential by any
  route, including the connector. But a connector edit removed the footer instead.
- *Claude Code locally:* the footer text, or code that builds it, would be in the local binary or
  settings. It is not. A change of rule would also need a client update; the survey's rule change
  came with none.
- *gh:* the footer would appear on bodies sent to any host with any credential. gh has no such
  feature and no such string.

**What cannot be decided without a write.**

1. Whether each REST operation stores a body sent in the footer form unchanged. #1565 is one
   instance for Issue-body PATCH, but it was not a single write under a grant for that write.
2. The exact append rule: whether it checks for an exact suffix; what happens when the footer is
   followed by a newline or appears earlier in the body; whether it applies to titles.
3. Whether writes that send no body change the stored body: a state-only PATCH such as a close,
   label changes, or a PR edit.
4. Which side of the egress boundary does it: the proxy or GitHub. No write from this container can
   decide it, because the App credential exists only beyond the proxy. Asking the operator of the
   proxy would decide it, but that sends material outside GitHub (§A.50 item 4) and needs the
   owner's approval.

These are not needed in order to write safely. Under §A.49 rule 2 the text sent is chosen from the
footer handling observed for the operation, and the expected stored text equals the text sent.
The validation writes in §3 settle items 1 and 3 for each operation used.

### D2. No stop on the first mismatch

From `edit.py` (evidence copy) and its replay under a mock (C1 in §4):

1. The read-back verdict is only printed: `print(num,'body match',rb==new)`. Execution continues
   to the label writes, and the driver calls `edit()` for the next Issue.
2. Label writes follow every body write unconditionally, and their result is not compared with
   an expected label set.
3. No persistent halt state exists, so a later run or another session can write again.
4. Pre-checks use `assert`, which `python -O` removes.
5. The operation (REST Issue-body PATCH) had not been validated. The text sent was not chosen
   from an observed footer handling for it. The form observed for REST comments (sent with the
   footer) was not applied.

Replayed with the actual `edit.py` code under the D1 behaviour, the run made 10 writes: 5 body
PATCHes and 5 label POSTs. Nine of them came after the first mismatch on #1558. That matches the
evidence README's account.

**Related near-miss.** `git push origin "$c:refs/heads/<branch>"` with `$c` empty produces the
refspec `:refs/heads/<branch>`, which asks to delete the remote branch. C2 reproduces this
against a fake `git` that only records its arguments.

**Root cause, common to both.** Write steps are not fail-closed. Failure is detected by printing
or by the exit status of an earlier step, and nothing structural stops the next write. The fix
is structural: one gate that every write passes through, which stops itself.

## 2. Correction: a single write gate

Every automated GitHub text write (body, title, comment, review, review comment), every label or
state change, and every `git push` goes through one gate. The prototype is `gate.py`. It reaches
the network only through an injected transport and git runner, and here it is exercised only with
the mocks in `mock.py`.

**G1. Halt marker first.** Before anything else, including any GET, the gate checks for the halt
marker. If the marker exists it raises `Halted` and nothing reaches a transport. The marker is
created with `O_CREAT|O_EXCL` and `fsync` and is never overwritten, so it keeps the first failure,
with its reason and digests of the sent and stored texts. The texts themselves are kept beside it
as evidence under §A.26. The gate never removes the marker. Only a person acting on a recorded
owner decision removes it (§A.49 rule 3).

**G2. Operation registry.** Each operation has its method, path, text fields, accepted status,
read-back path, and (from the owner's validation records) `validated` and `send_form` (`footer`
or `nofooter`). An unknown operation halts. An unvalidated operation halts unless the owner
granted a single write for that operation and target. The grant is consumed before the write, so
one grant allows one attempt (§A.51 item 2). In the prototype's default registry nothing is
validated.

**G3. Pre-checks (§A.49 rules 1 and 4).** No carriage return. No Unicode format character
(category Cf, including zero-width characters and the byte-order mark). No non-ASCII space. No
repository `blob`/`tree` link over 101 characters without a `#fragment`. No first line beginning,
after leading whitespace and in any case, with `oi-`. The body must match the operation's send
form. A failed pre-check halts; nothing is sent.

**G4. Expected text fixed before the write.** The expected stored text of each field is the text
sent, encoded as UTF-8 and hashed before the request. The send form decides whether that text
carries the footer. The gate never computes "sent plus footer" and never trims, strips or
normalizes. The comparison is byte for byte.

**G5. One write, then read-back.**
- Any exception from the transport during the write is treated as an unknown outcome and halts.
- A status outside the accepted set halts.
- A response to a create that names no object id halts.
- A created object is read back by the id in the response, never by the target number.
- Read-back by GET must return status 200 and an object, or the gate halts.
- Every sent field must match byte for byte, or the gate halts with the sent and stored texts as
  evidence.
- For PATCH, DELETE and label operations, the gate reads `title` and `body` before the write.
  Any of them not sent must be byte-identical afterwards. This catches a body changed by a
  state-only close.
- A close must read back as closed, and a label change must give exactly the expected label set.

**G6. Pushes.**
- The refspec must be exactly `<40 lowercase hex>:refs/heads/<designated branch>`. An empty
  source (a deletion), `+` (a force), a non-hex or short id, `main`, a tag, an undesignated
  branch or a remote name that starts with `-` is refused, and the refusal halts.
- Preflight reads the remote ref. It must be absent (create) or an ancestor of the commit
  (fast-forward).
- The command is fixed: `git push --porcelain -- <remote> <refspec>`. No flags are taken from
  input.
- A nonzero exit or an exception halts as an unknown outcome.
- After the push the gate reads the remote ref back, and it must equal the commit.

**G7. No batching past a failure.** The gate has no batch call. `run_plan` calls the gate once
per step and wraps nothing, so the first `Halted` ends the plan. A CLI wrapper exits with status
3 on `Halted`.

**Deployment notes (for the owner's decision; not implemented here).**
- Marker location. It should be a fixed path outside any worktree that every agent process on
  the host checks, such as one per-user state file, plus the git directory of each checkout. A
  marker on one host does not stop a session in another container. Cross-session effect therefore
  comes from the authorization side: a resumption names the designated writers (§A.51 item 1), and
  a halt in one writer leaves the others able to write until the owner revokes them. While
  validation is in progress, one designated text writer at a time removes this gap.
- Making the gate the only path. The token is injected by the proxy, so any process can call
  `gh api`. Using the gate is therefore a rule for the work package, not a technical barrier.
  Reviewers can check for it: a write made outside the gate is out of scope under §A.51 item 5.
- Comment read-back reads `issues/comments/{id}`. The read-back paths and the status of each
  operation are part of what validation fixes.

## 3. Validation protocol (§A.51 item 2)

An operation becomes validated when one write of it, made through the gate with the same tool and
path, under the owner's grant for that one write, passes exact read-back. The owner then records
it as validated, with its send form. Rules for every step:

- Each step needs its own owner grant, quoted with author and time. A step starts only after the
  previous one passed.
- Every step uses the footer form: the body ends exactly with
  `"\n\n---\n_Generated by [Claude Code](https://claude.ai/code)_"`, with no trailing newline.
  Titles carry no footer. The prediction for every step is that the stored text equals the text
  sent.
- Every target is one the owner designates, such as a scratch Issue the owner opens by hand. No
  step touches #1558, #1062, #1245, #1556 or #1565.
- A mismatch or unknown outcome writes the marker and ends validation. The evidence is kept under
  §A.26 and the owner is told. The halt stays until the owner decides otherwise.

| Step | Operation (REST, through `gh api` via the gate) | What the read-back checks |
|---|---|---|
| V1 | Comment create, `POST issues/{n}/comments` | body of `issues/comments/{id}` |
| V2 | Issue body edit, `PATCH issues/{n}` with `body` | body; title unchanged |
| V3 | Issue create, `POST issues` with `title` and `body` (only if creation is needed) | title, body of the created number |
| V4 | Label add, `POST issues/{n}/labels` | exact label set; title and body unchanged |
| V5 | Label remove, `DELETE issues/{n}/labels/{name}` | exact label set; title and body unchanged |
| V6 | Issue close, `PATCH issues/{n}` with `state`, `state_reason` only | state closed; title and body unchanged |
| V7 | `git push` creating one designated branch with one commit | remote ref equals the commit |
| V8 | PR create, `POST pulls` from that branch | title, body of the created PR |
| V9 | PR edit, `PATCH pulls/{n}` with `body` | body; title unchanged |

V1 to V6 can all use one scratch Issue, and V7 to V9 one scratch branch and PR. Whether the
REST-comment observation of 2026-11-23 already counts as V1 is for the owner to decide. Under
§A.51 item 2 it counts only if it was a single write under a grant for that one write.

**Optional diagnostic writes (characterization only; validate nothing).** These are made only on
a separate owner grant, while the halt stays in force.
- DX1: a comment create sent without the footer. The egress hypothesis predicts the footer is
  appended.
- DX2: an Issue body edit ending in the footer followed by `"\n"`. This tests whether the append
  rule checks an exact suffix.

A predicted mismatch is still a mismatch under §A.49: the gate halts, and the result is recorded
as evidence. These writes inform the choice of send form and are not needed to write safely.

## 4. Controls and results

All controls use the mock transport and a mock or fake `git`. None touches the network. To run
them: `python3 -I test_gate.py` and `python3 -I countercontrol.py`. Outputs are in
`results-tests.txt` and `results-countercontrol.json`.

**Control suite `test_gate.py`: 14 tests, all pass.** After every halt, a shared check tries
three more writes and pushes (a comment, a body edit and a push) through the same gate, and a
label write through a fresh gate. None may reach a transport, and the marker must exist.

| Test | Shows |
|---|---|
| 01 | Validated writes stored verbatim pass; no marker. |
| 02 | A mismatch halts; the marker records the reason and the sent and stored digests; no later write. |
| 03 | A replay of the five evidence bodies, in `edit.py`'s order, under append-if-absent: exactly one PATCH (#1558), then a halt. The mock's stored bytes equal the evidence `1558.stored.md`. |
| 04 | A read-back failure (connection error, or a 404) halts; no later write. |
| 05 | An exception during the write (unknown outcome) halts; no later write. |
| 06 | An unexpected status halts; no later write. |
| 07 | A marker that already exists blocks writes, closes and pushes, with zero transport calls (not even a GET), and it is not overwritten. |
| 08 | A marker blocks a separate Python process, which exits with status 3 after 0 writes. |
| 09 | CR, zero-width, NBSP, BOM, long blob link, `oi-` first line and missing footer are all refused before any write; a long line with a fragment link is accepted. |
| 10 | An unvalidated operation needs a single grant; the grant allows one write, and a second write halts. |
| 11 | A state-only close that changes the body is caught by the unsent-field check. |
| 12 | Label add and remove and a close pass with exact read-back. |
| 13 | An empty id, a short id, a non-hex id, an uppercase id, `+` force, `main`, an undesignated branch, a tag, an empty destination, an embedded refspec, `--delete` and a remote named `--force` are all refused with no git call. `check_refspec(":refs/heads/...")` names the deletion. |
| 14 | Create and fast-forward pushes pass with the fixed argv. A nonzero exit, an exception, a remote that does not move and a non-fast-forward all halt. |

**Countercontrols `countercontrol.py`: all three pass.**

- **C1.** The actual `edit.py` code from the evidence, with its `gh()` routed to the mock, under
  append-if-absent: 10 writes, 9 after the first mismatch. The no-subsequent-write predicate
  reports the violation. The same scenario through the gate makes 1 write.
- **C2.** The near-miss shell sequence (`c=$(false); git push origin "$c:refs/heads/evidence/x"`)
  against a fake `git` passed the arguments `push origin :refs/heads/evidence/x`, which is a
  deletion request. The gate refuses the empty id with no git call.
- **C3.** Mutation runs of the control suite. Baseline: 14 run, 0 failed.
  - Halt that prints and continues (the `edit.py` behaviour): 10 fail.
  - Halt-marker check removed: 11 fail.
  - Refspec check removed: 1 fails (test 13).

  Test 08 survives the in-process mutations because its subprocess imports the unmutated module.

The controls also found two defects in the first draft of the prototype, and both were fixed
before the recorded run. A created comment was read back by the Issue number instead of the
comment id, which test 01 caught. A remote name starting with `-` was accepted, which test 13
caught.

**Limits of these controls.** They show the gate's control flow, not the behaviour of the real
GitHub path. Real footer handling is established only by the validation writes in §3. The mock's
append-if-absent rule is modelled on the evidence, and test 03 checks it against the stored bytes.

## 5. What this protocol does not do

- It does not change AGENTS.md §A.49 or any other rule, and it does not weaken §A.49. The expected
  text is always the text sent, and no unexpected text is normalized away.
- It does not touch the bodies of #1558, #1062, #1245, #1556 or #1565, and it proposes no
  correction to them.
- It does not resume writing or lift the halt, validates no operation, and grants no write. Each
  validation step needs its own owner grant, and resumption needs a recorded owner decision
  (§A.49 rule 3, §A.51 item 5).
- It does not decide where D1 happens beyond the read-only evidence above. It sends nothing outside
  GitHub; a question to the proxy's operator needs the owner's approval (§A.50 item 4).
- It confers no scientific status and changes no frozen record.
